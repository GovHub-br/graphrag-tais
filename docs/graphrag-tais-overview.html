Arquitetura

Arquitetura de ponta a ponta

Da fonte de metadados ao gráfico no chat. À esquerda a indexação (batch); ao centro o motor de consulta (Haystack); à direita as entregas por pergunta.

Em uma frase: a indexação alimenta Qdrant e Neo4j; o motor usa os dois para recuperar o subgrafo e gerar SQL com o LLM; a entrega executa o SQL e produz os quatro artefatos por pergunta.

Camadas de dados

Da fonte ao grafo + vetores

O graphrag-tais não modela dados — consome o schema já construído (dbt), catalogado (OpenMetadata) e o transforma em grafo (Neo4j) + vetores (Qdrant).

1.Camada semântica (a fonte)

PeçaPapelSaída p/ o RAG
dbtTransforma os dados brutos nas tabelas analíticas (bronze → silver → gold) no Postgres cidades.as tabelas físicas que o SQL consulta
MetricFlowCamada de métricas de negócio (semantic layer).vocabulário de métrica (evolução)
OpenMetadataCatálogo: descrições, tipos e as “relações semânticas MCID” (Custom Property) que definem os JOINs.fonte única da ingestão (REST)
Ponto-chave: o MCid não declara Foreign Keys — a joinabilidade vem das Custom Properties e vira as 24 arestas SEMANTIC_JOIN (adapter mcid_markdown_v1).

2.Ingestão (orquestrada por Airflow)

  1. OpenMetadataSource — lê o snapshot do catálogo via REST (escopo do .env).
  2. MetadataRecordBuilder — normaliza no contrato Table/Column/Relationship; extrai os SEMANTIC_JOIN.
  3. GraphCardBuilder — projeta em nós/arestas + um card de texto por entidade.
  4. Neo4jGraphWriter + GraphWriteGate — grava o grafo; só libera os embeddings após o Neo4j confirmar.
  5. Embedders → Qdrant — card → denso (Ollama) + esparso (BM25). Costura por node_id.

3.Qdrant — busca vetorial

Acha os pontos de entrada: busca híbrida (denso + esparso) fundida por RRF.

AspectoComo
DensoOllama gte-qwen2-1.5b (1536 dims, multilíngue) — semântica
EsparsoBM25 (Qdrant/bm25) — casa identificadores exatos
Fusão + tuningRRF + filtro de scope_id + pool 30 + corte determinístico (-score, node_id)

4.Neo4j — a “costura” do GraphRAG

A partir das sementes, percorre o grafo e monta o subgrafo: tabelas, colunas (podadas) e JOINs.

Fato do grafo realValorConsequência
Tabelas ilha (sem JOIN)55 / 74maioria das perguntas é mono-tabela
Joins que cruzam schema0sem contaminação entre domínios
Joins elegíveis (diretos)6 / 24o resto exige normalização
Grau do hub cadastro_pj8fonte do inchaço de contexto
Custom: Neo4jSubgraphRetriever expande por SEMANTIC_JOIN (modo evidence) e poda colunas ao essencial (PK + chaves de JOIN + sementes + casadas com a pergunta).

Motor de consulta

Haystack, modelos e a pipeline

Haystack modela cada etapa como um componente; o Hayhooks serve as pipelines como REST OpenAI-compat (é o que faz o open-webui enxergar o modelo query).

2.Modelos — embedding & LLM

PapelModeloOnde
Embedding densogte-qwen2-1.5b-instruct (Ollama)on-prem · 1536 dims
Embedding esparsoQdrant/bm25 (fastembed)local · lexical

Privacidade & invariante: só a pergunta e os metadados vão pra OpenAI — as linhas do banco nunca saem (ADR-0009). Ingestão e query têm que usar o mesmo modelo de embedding, senão os vetores não são comparáveis.

3.Pipeline de consulta (passo a passo)

  1. Embeddings da query — denso (Ollama) + esparso (BM25), os mesmos da ingestão.
  2. Busca híbrida no Qdrant — RRF + scope + corte determinístico → sementes (top-5).
  3. Subgrafo no Neo4j — expande por SEMANTIC_JOIN (evidence) e poda colunas → tabelas + JOINs.
  4. LLM (gpt-4o) — uma chamada JSON interpreta a pergunta (IR) e escreve o SQL.
  5. SqlAnswerBuilder — explicação + SQL + dicionário de dados + IR (ponto de controle ADR-0006/0007).

Produto

Entregas por pergunta (a · b · c · d)

O produto não entrega “um SQL” — entrega quatro artefatos por pergunta (ADR-0010). A entrega é uma pipeline separada que compõe o motor.

#EntregaComo é feitaStatus
aTabelas · colunas · SQLSqlAnswerBuilder — dicionário de dados ancorado no subgrafopronto
bGráfico do indicadorLLM emite chart-spec validada nas colunas reais → matplotlib → PNG base64pronto
cExplicação do resultadoLLM comenta os números executados, com ressalva de grainpendente
dRelatório .docxdocxtpl + imagem embutida, hospedado no MinIOpendente

Execução do SQL (o que destrava b · c · d)

McpSqlExecutor

Agent que se autocorrige

Um Agent do Haystack + postgres-mcp (read-only) roda o SQL; no erro, lê a mensagem, corrige e tenta de novo até AGENT_MAX_STEPS.

chart-spec + renderers

O LLM escolhe, o matplotlib desenha

O LLM decide o tipo de gráfico e os eixos (validado nas colunas reais); o matplotlib desenha de forma determinística.

Limitação de grain (E2E): empreendimento/ficha_empreendimento têm cada APF duplicado (1.646 linhas p/ 823 APFs) → o renderer soma duplicatas e dobra valores. Guardrail de dedup pendente.

Qualidade · desenvolvimento orientado a métricas (ADR-0012)

Tuning do retrieval

Partindo de um audit (muito contexto + recall baixo), duas fases medidas ao vivo contra o gold (8 casos). Regra: medir antes, medir depois, só adotar se os guardrails segurarem.

o que fizemos

Fase 1: scope filter + fusão determinística + poda de colunas. Fase 2: expansão por evidência. Segurança: 100% das colunas e tabelas-gold preservadas.

o que falta

Seed recall ~30% é o gargalo (não tocado). Próximo lever: prefixo de instrução no GTE (lado da query, sem reindexar). Prompt p95 ainda > alvo de 12k. Gold draft / 8 casos.

Como rodar

# Docker Desktop + VPN da lab (rede 10.0.0.x: Ollama e o banco)
make up                       # qdrant, neo4j, hayhooks, postgres-mcp
docker compose up -d webui    # chat em :3000 (modelo "query")
curl -X POST localhost:8000/ingest/run -d '{}'   # ingestão
Gotchas: a rede 10.0.0.x exige a VPN da lab · 429 da OpenAI = cota esgotada · com ~7,75 GiB de RAM, Airflow + RAG + webui juntos dão OOM (pare o Airflow para testar o chat). Verdade operacional completa: CLAUDE.md.
